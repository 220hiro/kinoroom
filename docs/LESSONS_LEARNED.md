# Уроки разработки и инженерные решения (Lessons Learned)

Этот документ фиксирует ключевые инженерные выводы, сделанные в ходе разработки KinoRoom, чтобы исключить повторение ошибок при дальнейшей работе с OpenAI Codex.

---

### 1. Нельзя подменять TMDB ID демонстрационным фильмом
* **Почему**: Если пользователь открывает конкретный фильм (например, «Аватар» или «Бойцовский клуб»), а система незаметно запускает демонстрационный ролик «Tears of Steel», доверие пользователя полностью разрушается.
* **Решение**: При отсутствии проверенного видеопотока API строго возвращает `HTTP 404 SOURCE_UNAVAILABLE`. Демонстрационные видео доступны только по их явным идентификаторам.

### 2. Нельзя показывать фиктивную озвучку или качество
* **Почему**: Если в карточке написано «Русский дубляж 1080p», а видео идёт на английском языке в 480p, интерфейс вводит пользователя в заблуждение.
* **Решение**: Отображать только подтверждённые аудиодорожки и уровни качества, полученные из манифеста HLS или метаданных торрента.

### 3. HTTP 200 и успешная загрузка iframe не доказывают воспроизведение
* **Почему**: Внешний сервис может вернуть HTTP 200 со страницей ошибки «Видео удалено», плеером с геоблокировкой или рекламным заглушечным экраном.
* **Решение**: Успешной интеграцией считается только реальное декодирование кадров и старт воспроизведения аудио/видео на клиенте.

### 4. controls=false не удаляет рекламу из стороннего плеера
* **Почему**: Параметр `controls=false` лишь скрывает интерфейсные кнопки плеера iframe. Сам провайдер (CineSrc, EmbedWave) по-прежнему содержит скрипты, открывающие popup-окна и редиректы при клике или касании экрана на мобильном устройстве (что подтвердилось при тесте на реальном iPhone в Шаге 2G).
* **Решение**: Сторонние рекламные iframe отвергнуты как целевая архитектура проекта. Основной фокус — собственный нативный плеер и чистый видеотранспорт.

### 5. HTML-оверлей нельзя считать полноценными встроенными субтитрами
* **Почему**: Внешний оверлей в DOM (`<div>` поверх плеера) не является частью видеоряда. На мобильных устройствах (iOS) при переходе в системный полноэкранный плеер QuickTime этот слой отсекается.
* **Решение**: Для сторонних iframe оверлей является компромиссным решением. В собственном плеере субтитры должны рендериться нативно через WebVTT textTracks.

### 6. CSS Fullscreen не равен нативному Fullscreen на iPhone
* **Почему**: Safari на iPhone не поддерживает `element.requestFullscreen()` для произвольных контейнеров (поддерживается только `HTMLVideoElement.webkitEnterFullscreen()`). Режим `fixed inset-0 z-50` разворачивает элемент в пределах окна браузера, но интерфейс Safari (панель URL и нижняя панель) остаётся частично видимым.
* **Решение**: Разделять термины: «Системный полноэкранный плеер iOS» (скрывает DOM) и «Псевдо-полноэкранный режим / Cinema Mode» (сохраняет DOM).

### 7. Cross-origin iframe не даёт прямого доступа к video и textTracks
* **Почему**: Политика безопасности Same-Origin Policy браузера строго блокирует доступ родительской страницы к содержимому `iframe.contentDocument` стороннего домена.
* **Решение**: Взаимодействие возможно исключительно через документированный протокол `window.postMessage`, если он поддерживается и транслируется провайдером.

### 8. Зелёные unit/E2E-тесты не заменяют живые тесты на устройстве
* **Почему**: Headless Chromium в тестах не воспроизводит ограничения мобильной операционной системы (требование тача пользователя для звука, поведение QuickTime на iOS, всплывающие окна мобильных рекламных сетей).
* **Решение**: Финальным критерием готовности любой мультимедийной функции является ручная проверка на реальном iPhone владельца.

### 9. Нужно подтверждать конкретный SHA опубликованного Vercel Preview
* **Почему**: Если агент запушил коммит и сразу предоставил общую ссылку на Preview-домен, Vercel может ещё находиться в процессе сборки или закэшировать предыдущий деплой.
* **Решение**: Всегда проверять статус сборки и подтверждать, что деплой на Vercel соответствует последнему commit SHA.

### 10. Vercel Serverless не заменяет постоянно работающий торрент-движок
* **Почему**: Бессерверные функции Vercel имеют таймауты (10–60 секунд), не сохраняют состояние между запросами и не могут поддерживать постоянные P2P-сессии по протоколам BitTorrent (TCP/UDP/uTP).
* **Решение**: Торрент-стриминг требует постоянного сервера (локальный запуск или VPS с Docker/TorrServer). Vercel используется для фронтенда и API метаданных.

### 11. Нельзя писать большой компонент до проверки критических технологических ограничений
* **Почему**: Создание огромного компонента плеера на 1100 строк (как в Шаге 2G) до проверки поведения рекламы CineSrc на реальном iPhone привело к необходимости полного отката работы.
* **Решение**: Сначала создавать минимальный PoC (Proof of Concept), проверять его на целевом устройстве, и только после подтверждения приступать к интеграции.

### 12. Нельзя гарантировать отсутствие рекламы на основании одного только URL
* **Почему**: Бесплатные провайдеры эмбедов могут менять рекламную политику динамически на стороне своего сервера в зависимости от User-Agent и географии.
* **Решение**: Не давать пользователю ложных обещаний «100% без рекламы» для внешних интеграций.

### 13. Нельзя считать скорость torrent swarm доказательством отсутствия буферизации
* **Почему**: Высокая скорость роя (например, 2.4 МБ/с) показывает среднюю скорость скачивания, но если куски скачиваются непоследовательно (random pieces вместо sequential), плеер будет зависать в ожидании следующих байтов таймлайна.
* **Решение**: Требуется принудительный sequential download (последовательное скачивание) и приоритет для заголовков файла.

### 14. Не следует обещать выбор качества при наличии одного фиксированного потока
* **Почему**: Если видеоисточник отдаёт один MP4-файл или HLS-поток с одним вариантом битрейта, выпадающий список «1080p / 720p / 480p» является фикцией.
* **Решение**: Отображать выбор качества только тогда, когда HLS манифест содержит реальные варианты `#EXT-X-STREAM-INF` с разными разрешениями.
