## Этап 1: запуск длинного файла до полной загрузки — передача Antigravity

Реализован локальный progressive режим в `scripts/torrent-hls-pilot.mjs`. Собственный testsrc2/sine fixture повторён без перекодирования до 5400.097 сек: HEVC Main/MP3, 720p, 956 220 505 байт. Это синтетический файл, не фильм. Два WebTorrent клиента передают его по настоящему TCP loopback; один явный peer, metadata известны заранее, публичный рой/trackers/DHT отключены. Sender ограничен 512 КиБ/с. Store дисковые, receiving cache отдельный для каждого run; весь файл в RAM не читается.

Путь: receiving WebTorrent → HTTP source с окнами 2 МиБ (`torrentRangeReader.ts`) → FFmpeg video copy/hvc1 + AAC → EVENT fMP4 → Next proxy → существующий TorrentPlayer. Readrate=1/initial burst=20; playlist выдаётся после init и трёх завершённых сегментов, `.tmp` не выдаются. Reader учитывает отмену/backpressure. Обычный raw route не использует этот bounded reader.

|---|---|
| Metadata | Таймер ожидания 12 сек повторяется в stream route, до примерно 142 сек без metadata. Это верхний сценарий по коду, не измеренный запуск фильма. Новая метрика metadataObservedMs и request metadataWaitMs. |
| Подключение | DHT/trackers включены; сеть и наличие раздающих нужный кусок пиров неизвестны. Метрики firstPeerObservedMs, peers и peersWithNextPiece для WebTorrent. |
| Нужные части | Sequential уже default; range priority 1. Фоновая загрузка всех файлов возможна. nextPieceAvailable — снимок наличия verified piece, не доказательство stall само по себе. |
| Буфер | Torrent.ready означает metadata, а onWaiting включает тот же UI-флаг загрузки. Probe измеряет действительный buffered ahead и продолжительность ожиданий, отделяет начало от rebuffer. |
| Decode | MIME/расширение не проверяет codec. Существующая ошибка MEDIA_ERR_DECODE/SRC_NOT_SUPPORTED и первые loadeddata/представленный frame выявят клиентскую часть. Полного разбора codecs пока нет. |

### Минимальное исправление по данным

В `getOrAddTorrent` и upload route добавлено `deselect: true`; в stream route удалён постоянный `file.select()`. Метаданные и status больше не запускают полную загрузку новой раздачи. Каждый `file.createReadStream` сохраняет собственную selection, включая несколько зрителей; при закрытии она удаляется средствами WebTorrent. Готовые куски остаются в существующем кеше. Нет нового движка, источника или компонента плеера.

Обычный открытый Range `bytes=N-` по-прежнему охватывает остаток файла — это не ограниченное окно prefetch. Если браузер держит такой HTTP request открытым, скачивание может продолжаться. Устраняется постоянная фоновая selection, а не любой трафик при Pause; остаются уже отправленные in-flight blocks и seeding. Проверка бинарных ranges/нескольких читателей выполнена на реальном TCP loopback WebTorrent с собственными сгенерированными байтами, без trackers/DHT/public swarm. Это подтверждает передачу диапазона и остановку payload после закрытия, но не ускорение фильма.

Уже добавленные torrent в глобальном клиенте сохраняют старую selection через HMR. Для проверки новой политики нужен новый инстанс torrent/процесса; работающий dev автоматически не перезапускался. Сравнение прежнего холодного старта с уже прогретым дисковым кешем некорректно. Нужен отдельный контроль до/после на разрешённом материале с одинаковым состоянием кеша.

- **Подтверждён дефект, связь с наблюдением неизвестна:** старый Range parser превращал bytes=-N в start=NaN и end=N. Хвостовые запросы метаданных MP4 могли ломаться. Исправлены suffix, open-ended, clamp end и отказ на malformed/reversed ranges. Исправление действует только на WebTorrent route, не на прямой TorrServer.
- **Высокая уверенность в риске по коду:** getOrAdd ждёт metadata/ready или 12-секундный timeout и затем разрешает promise даже без metadata. Stream route повторяет это до десяти раз с секундными паузами: при отсутствии metadata ожидание может приблизиться к 142 секундам. Реальная задержка данного сеанса неизвестна.
- **Фоновая загрузка подтверждена trace:** после закрытия HTTP streams скачивание продолжалось. Конкуренция за сеть/диск как причина задержки seek остаётся гипотезой; её устранение требует сравнения после patch. Sequential уже работает; слепое добавление sequential не является исправлением.
- **Средняя уверенность как гипотеза:** медленное получение именно следующего verified piece, плохой swarm, высокий битрейт, metadata в хвосте или неподдерживаемый контейнер/кодек. Не доступны исходный файл, trace и параметры конкретного роя.
- **Подтверждён риск UI:** polling повторно навязывает файл, конфигурация TorrServer загружается асинхронно после возможного старта WebTorrent, ready не равно первому кадру. Частота/влияние на пользовательский сеанс неизвестны.

MP4 moov в конце не обязательно требует скачать весь фильм: исправный Range transport позволяет получить хвост. Утверждение HANDOFF об обязательной полной загрузке некорректно.

## K. Ограничения и варианты транспорта

| Вариант | Что даёт / границы / решение этапа |
|---|---|
| A. WebTorrent | Сохранить для измерения Range и приоритетов. Нет автоматической смены кодека/аудио/качества. После trace рассмотреть deselect фоновых файлов и lifecycle, без глобального deselect при нескольких зрителях. |
| B. Отдельный TorrServer | Долгоживущий P2P и его кеш вне Vercel. Нужны реальные version/config, cache/preload, swarm и logs без секретов. /gst/... требует соответствующей сборки, наличие сервером не проверяется; обычный TorrServer не гарантирует HLS/transcode. Пользовательский localhost/private URL блокируется API SSRF-политикой; доверенная server env конфигурация проходит другой путь. |
| C. HLS + cache/remux/transcode | Packaging способен дать реальные renditions/дорожки; remux не исправляет неподдерживаемый codec, transcode требует CPU/GPU. Нагрузку и бюджет пока нельзя рассчитать без codecs/bitrate/concurrency. Ничего не развёрнуто и не куплено. |
| D. Прямой MP4/HLS | Предпочтителен для совместимого разрешённого источника: отсутствует этап discovery роя. Один файл не является ABR. |

Chrome/Safari поддержка зависит от codec, платформы и контейнера; нужен реальный decode, не проверка расширения. Safari iPhone требует user gesture, отдельной проверки native fullscreen/textTracks. DOM overlay там недостаточен. Vercel не является постоянным P2P worker; точные лимиты тарифа здесь не проверены, цифры 10–60 секунд из документов нельзя считать актуальными.

## Минимальная локальная диагностика

### Неудачный запуск на iPhone

Владелец сообщил, что после «Буферизация потока» видео на iPhone не начинается; раздача предположительно та же, что на ноутбуке. На сервере не зафиксированы stream/info errors, но успешные HTTP requests и MediaError iPhone этим логом не измерялись. Точную причину AVPlayer без события с устройства нельзя объявлять доказанной.

Проверены четыре локальных torrent stores: DocType `matroska`, не MP4. Кодеки определены разбором EBML TrackEntry/CodecID, а не поиском слов в названии. Файл с размером, совпадающим с первым HTTP range из присланного laptop trace (4775947138 bytes), имеет видео `V_MPEGH/ISO/HEVC` и звук `A_MPEG/L3`. Остальные файлы: AVC с AC3, либо AVC с AAC/AC3/EAC3. Имена и исходное содержимое в проект не сохранялись. Наличие store не устанавливает, какой именно файл был выбран на iPhone; ответ «одну и ту же вроде» оставляет эту привязку вероятной.

Текущий путь отдаёт MKV как `video/x-matroska` без remux/transcode. Для Safari Apple рекомендует H.264 MP4 или HLS: https://developer.apple.com/documentation/webkit/delivering-video-content-for-safari . Совместимость контейнера/кодеков — основная версия отказа для того же файла; скорость роя её не исправляет. Подмена MIME/расширения ничего не конвертирует. Remux или transcode не реализованы; решение об обработке медиа требует отдельного согласования.

Дополнительно подтверждены два дефекта приложения:
- `togglePlay` преждевременно выставлял isPlaying/hasStartedPlaying и не обрабатывал отказ `play()`; счётчик ожидания мог остановиться, хотя первый кадр ещё не появился.
- Эвристика «MP4 для iPhone» принимала AVC/H.264/mobile слова за контейнер MP4, хотя скачанные AVC-файлы реально MKV.

Исправлено локально: UI опирается на onPlay/onPlaying; отказ play Promise прекращает ложное состояние и показывает фиксированное сообщение для NotSupportedError/NotAllowedError/AbortError, без вывода error.message. Resume/retry используют ту же обработку. Предположения о MP4 теперь требуют явного слова MP4 и маркируются как заявления по названию; видеоисточники не удалены, новый плеер/конвертер не создан.

Проверки после исправления: typecheck/build успешно, unit 45/45, Chromium E2E 27/27. Контрольные отказы Play прошли также в desktop WebKit (2/2); это mocks и не реальный Safari iPhone. Начальный WebKit fixture ошибочно ждал decoder error до нажатия Play и истекал по timeout; тест отделён от preload/decoder поведения, assertions обработки отказов сохранены.

Обновлённый локальный сервер для iPhone перезапущен на 192.168.31.147:3001 (exec session 69922); /torrent и /player-test ответили 200 с ноутбука. Владелец подтвердил воспроизведение контрольного HLS на реальном iPhone. Этот результат относится к отдельному HLS-источнику; P2P, исходный MKV и точная причина AVPlayer им не подтверждаются. Повтор контрольного HLS сейчас не нужен.

### Выбор следующего решения после контроля HLS

Владелец согласовал локальный пилот Torrent → HLS. Первоначально проверена portable TorrServer-GST MatriX.146.1: checksum совпал с GitHub, но /gst/echo завис при загрузке встроенного runtime. Автоматическая проверка отклонила два перезапуска с «blocked by policy», подробной причины не предоставила. Повторные попытки запуска GST прекращены; выбран отдельный локальный пилот существующего WebTorrent + portable FFmpeg. В TorrentPlayer предусмотрен /gst/{hash}/master.m3u8, но эта интеграция и контракт index по-прежнему не подтверждены. Обычный backend не переключён.

- Быстрый вариант без обработки — реальный MP4 с совместимыми H.264/AAC. Проверять метаданные файла, а не название раздачи. Это не устраняет отсутствие нужных кусков у пиров.
- Основной вариант — remux совместимого видео в HLS; видеопакеты копируются без перекодирования и потери качества. Если нужна совместимость звука, преобразовывать только звук в AAC. HEVC допустим при поддержке конкретного устройства и корректной упаковке в fMP4; сам HEVC не объявляется причиной отказа.
- Полное перекодирование видео в H.264 — только если профиль/кодек несовместим и после измерения CPU/RAM и скорости. Цена одновременных просмотров здесь не рассчитана.
- Существующие ссылки на VLC/Outplayer — обходной путь через внешнее приложение, не результат для собственного браузерного плеера.

Пилот должен измерить время первого кадра, отсутствие зависаний и seek в ещё не загруженную область, а также CPU/RAM/кеш. HLS не гарантирует быстрый seek: нужны индекс источника, запрос частей у точки перемотки и создание сегментов по требованию; последовательная конвертация от начала этого не обеспечивает. Слабый рой остаётся ограничением любого packaging. Обработка требует постоянного локального/отдельного процесса, Vercel не выбирается для P2P/packaging.

Первичные источники проверены 2026-10-14: [Apple HLS specification](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html) (HEVC в fMP4), [FFmpeg streamcopy](https://ffmpeg.org/ffmpeg.html#Streamcopy) (без decode/encode), [TorrServer GStreamer](https://github.com/YouROK/TorrServer#GStreamer) (специальный -gst binary, HLS/remux/transcode; Windows embedded runtime зависит от сборки). Документация upstream не доказывает работу интеграции KinoRoom.

### Базовый короткий VOD-пилот WebTorrent → FFmpeg → HLS (до этапа 1)

Файлы: scripts/torrent-hls-pilot.mjs, src/lib/playback/hlsPilot.ts, pilotVideoDiagnostics.ts, /torrent-pilot и /api/torrent/hls-pilot/[...path]. Новый плеер не создан: страница использует существующий TorrentPlayer с явно заданным экспериментальным режимом. Режим выключен без KINOROOM_HLS_PILOT=1 и всегда выключен при VERCEL. Proxy target всегда 127.0.0.1, порт default 8092 меняется валидированным KINOROOM_HLS_PILOT_PORT; доступны только status/events и известные HLS-файлы, никакого произвольного URL или source endpoint через Next нет.

Собственный ролик с testsrc2/sine: 120 секунд, 1280×720/24 fps, HEVC Main/MP3, 21 255 977 байт. Названия принимаемых fixtures фиксированы, размер короткого VOD fixture ограничен 64 МиБ. Два настоящих WebTorrent клиента передают его через TCP loopback; известные torrent metadata переданы напрямую, один peer добавлен явно. DHT/trackers/LPD/NAT/uTP/webseeds выключены. До обращения FFmpeg за HTTP Range получено 0 payload bytes. Это не внешний swarm и не замер поиска metadata из magnet.

FFmpeg запускается только для fixture, с -c:v copy -tag:v hvc1 и AAC LC/stereo. Получаются init.mp4 и fMP4 сегменты, а также VOD playlist. Данные получены из receiving torrent, не читаются FFmpeg напрямую из исходного дискового MKV. Probe готового выхода подтвердил HEVC/hvc1, AAC/mp4a, 1280×720, 48 kHz/stereo, duration 120.059 секунды.

Установки в ОС и изменения PATH нет: portable программы хранятся вне Git в LOCALAPPDATA/KinoRoom/gst-pilot. FFmpeg Windows build BtbN n9.0 взят через ссылку с официальной страницы FFmpeg, SHA256 архива сверена с GitHub asset metadata. Для генерации исходного AVC fixture использовались lavfi testsrc2 (720p/24 fps) и sine (440 Hz/48 kHz), libx264 veryfast/CRF24/GOP48, libmp3lame 128k, duration 120; затем libx265 ultrafast/CRF28/GOP48 с копированием MP3. Это собственные синтетические данные, не коммерческий фильм.

Важный предел короткого VOD режима: он сначала получает и переупаковывает ВЕСЬ двухминутный clip. Так нельзя объявлять готовым онлайн-просмотр длинного фильма или seek в незагруженную часть роя. Преимущество скорости перед исходным фильмом не измерено.

Видео автоматически отправляет только временный session tag и числовые media events/buffer/readyState/errorCode/размер кадра на тот же локальный origin. Worker держит максимум 200 строк в памяти; не сохраняет URL, IP, User-Agent, имена, токены или произвольные ошибки. Следующий Codex turn может читать /events и /status на loopback без DevTools на iPhone.

Добавлен `src/lib/services/torrentDiagnostics.ts`. Требуется `KINOROOM_STREAM_DIAGNOSTICS=1`; при NODE_ENV=production отключён даже с флагом. Участки подключения — `getOrAddTorrent`, `getTorrentStatus` и HTTP stream adapter. В слабой карте объектов хранится только текущая сессия, активные запросы и небольшой хвост завершённых запросов. Дополнительных сетевых запросов и логирования нет, диагностика возвращается в существующем status JSON.

Для WebTorrent: время первого наблюдения metadata и первого wire от начала наблюдения; признак уже имевшихся metadata; время подготовки HTTP stream; время первого переданного chunk; число байтов, добавленных в HTTP stream; доступность следующего куска и число текущих wires с ним. Это снимок состояния, а не накопленное время ожидания кусочка. Снимок обновляется при существующем status polling примерно каждые 2.5 секунды; короткие задержки могут остаться между снимками. Отсутствие следующего куска само по себе не доказывает stall декодера. При переиспользовании torrent начальное время неизвестно и явно помечается metadataAlreadyAvailable.

`scripts/playback-probe.js` теперь устанавливается **до выбора раздачи**, даже без video в DOM. Он слушает события video и наблюдает существующие fetch status-ответы, возвращая приложению исходный Response. Собирает только разрешённые числовые поля; секреты, URL, названия, hash и адреса пиров не экспортирует. Разделяет сессии при loadstart, startup/rebuffer/seek, считает задержку seek до seeked и до playing. Время loadedmetadata/canplay/firstRenderedFrame отсчитывается от loadstart; playingMs включает ожидание касания Play, если пользователь нажал поздно. Если loadstart произошёл до подключения probe, полного замера старта нет.

Для TorrServer доступны browser events и нормализованные peers/downloadSpeed из существующего API, но внутреннее ожидание его кусков не измеряется. Для HLS через blob источник помечается mse, а backend выясняется по statusBackend. Проверка фактического decode — события loadeddata/playing и requestVideoFrameCallback, а не metadata.ready.

Ручная проверка реального iPhone остаётся обязательной перед признанием воспроизведения готовым, но текущий следующий шаг — один ноутбучный тест; дальнейшие этапы ждут его результата.
